```
cp <file>.js /tmp/chk.mjs && node --check /tmp/chk.mjs
```

This is not cosmetic: the real `.mjs` check is what caught a leftover `}, "MIXED")` patchFunc tail in `monks-enhanced-journal.js` (see `monks-enhanced-journal.js` silent takeover 10) that the `.js` check had passed. That ruling is correct for the *shell* (`apps/enhanced-journal.js`) and wrong for the *standalone* sheet, because the two classes get their `configureSheet` entry from different places:

- `EnhancedJournal` extends `ApplicationV2`, whose `DEFAULT_OPTIONS.window.controls` carries only Detach and Attach (`client/applications/api/application.mjs:68-79`). Its single `configureSheet` control is the one the fork declares in its own `DEFAULT_OPTIONS`, so `super._getHeaderControls()` returns it exactly once — filtering it out would delete the control outright.

Because `ApplicationV2.#mergeApplicationOptions` **concatenates** arrays, `super._getHeaderControls()` yields core's `configureSheet` — and `_documentControls()` (`sheets/EnhancedJournalSheet.js:1696-1701`) pushes the fork's own `configureSheet` entry on top of it. Without the filter, a GM on an editable standalone MEJ sheet sees **"Configure Sheet" twice**.

Resolved to 14.01's exact form:

```js
    _getHeaderControls() {
        if (this.enhancedjournal)
            return [];
        let controls = super._getHeaderControls();
        controls = controls.filter(c => c.action != "configureSheet");
        return [...controls, ...this._documentControls().filter(c => !c.type || c.type == "button")];
    }
```

So the final rule across the two files is: **standalone sheet keeps the filter, shell does not.** Our `_documentControls()` button list is kept in both cases.

It is core's own handler on a real `JournalEntryPage`, gated by `DocumentSheetV2.#canConfigureOwnership`, and is the same entry every other v14 document sheet shows — kept deliberately rather than filtered, alongside Detach/Attach which is the reason the `super` merge was adopted in the first place.
